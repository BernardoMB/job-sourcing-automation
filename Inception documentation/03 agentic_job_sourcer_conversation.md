🔄 The Walk-Away / Briefing / Batch-Execute Loop
-----------------------------------------------

This is the heart of the harness. The

### Phase 1: Silent Accumulation (You are away)

Watchers poll at a modest interval

you configure a digest rule: "Batch all pending drafts into one briefing when I

### Phase 4: Batch Execution (The agent acts)

1. Reads every draft with

2. Groups them by action
   type.
3. Runs them **sequentially with idempotency guards** (so a retry never sends the same email twice).
4. Logs every outcome to
   `execution_log`.
5. Marks drafts as
   `executed_at = now()`.

The executor uses
`holdpoint`'s exactly-once execution guarantee:
"Fifty concurrent approvals of one action execute it once; the other forty-nine
wait and return the same stored result". This matters
because a bug in your loop should never send a recruiter three identical
replies.[-1](https://pypi.org/project/holdpoint/0.1.0/#1)

🧠 The "Don't Ask Again" Learning Subsystem (Detailed)
-----------------------------------------------------

This is the part that makes the harness
feel like it's building judgment. It has **three
tiers of autonomy**, matching the proven
`auto / escalate / review` routing
trichotomy.

### Tier 1: `ask` (default)

Every draft goes to the briefing.
Nothing is sent without your decision. This is the safe starting state.

### Tier 2: `auto_approve` (earned autonomy)

When you click "Don't ask again" and
choose `auto_approve`, the agent skips the
briefing **only when confidence is above a
threshold** (default 0.9). If the LLM is less
certain, the draft still appears in the briefing. This gives the agent "earned
autonomy" without blind trust—the same
`ask → notify → auto-within-caps` ladder used by
the Nova project.

### Tier 3: `auto_send` (full delegation)

This is the "don't even show me" tier.
It should be reserved for **low-risk,
high-repetition** categories only:

* "Thank you, I'll review and get
  back to you."
* "Yes, I'm open to hearing about
  the role."
* "My availability for a call is
  [calendar-derived slots]."

**Never** enable `auto_send` for salary
discussions, offer negotiations, or anything that makes a commitment you haven't
explicitly authorized. The `decision_rules`
table has an `auto_approve` flag; add a
separate `auto_send` flag and a
`max_risk_level` column so you can enforce this in
code.

### Rule Matching Logic

When a new event arrives, the reasoning
engine does **not** ask
"should I draft a reply?" It first checks:

text

Copy

Download

```
1. Does this event match any active decision_rule?
   - If YES and rule.auto_send = 1 and risk_level <= rule.max_risk:
        → execute immediately (log it, but don't brief).
   - If YES and rule.auto_approve = 1 and confidence >= 0.9:
        → execute immediately (log it).
   - If YES and confidence < 0.9:
        → create draft, status = 'pending' (brief it).
   - If NO:
        → create draft, status = 'pending' (brief it).
```

This is the mechanism that turns your
"Don't ask again" clicks into persistent behavior. Every time a rule matches,
`times_matched` increments, giving you a dashboard
metric: **"This rule has handled 14 events without
asking you."**

⚠️ Critical Design Decisions to Lock In Early
---------------------------------------------

1. **Executor
   isolation**: the executor must be a
   separate process (or at least a separate function) that is
   **only invoked after the briefing loop
   ends**. Do not let the LLM call
   `send_email` directly during reasoning. The
   LLM produces a draft; the executor acts on approved drafts. This is the
   single most important safety invariant.
2. **Idempotency**: every action
   gets a deterministic `idempotency_key`
   (e.g., `sha256(event_id + action_type + payload)`). The executor checks this key before running. This is what
   prevents double-sends when you retry a failed batch.
3. **Confidence thresholds
   are configurable per rule**: a
   `tech_question` rule might auto-approve at
   0.85, while a `salary_question` rule
   might require 0.98 or always ask. Store this in
   `decision_rules`.
4. **LinkedIn rate limits are
   non-negotiable**: respect the toolkit's
   hourly and daily caps. Your harness should never try to "speed up"
   LinkedIn by running parallel sessions. The whole point of using the
   toolkit is that it operates at human pace.
5. **Audit
   everything**: every draft, every
   decision, every execution goes into
   `execution_log`. When a recruiter says "you
   told me X," you can trace exactly which draft produced that message and
   who approved it.

🧠 Subagent 1: The CV Analyst (New Requirement 1 & 1.5)
------------------------------------------------------

**Purpose**: Answer recruiter questions about your experience, technologies, and
years of experience by reading your markdown CV—**without ever asking you**.

### Implementation

Use the
**`resume-mcp-server`**. It parses
`.md` files into structured data (work history,
skills, achievements) and exposes **19 read-only
tools** for searching by skill, company, role,
or full text. Critically, every tool is annotated

### The "I Don't Want to Reply" Guarantee

The CV Analyst is **read-only and deterministic**. It does
not generate free-text answers on its own; it retrieves **exact evidence** from your CV. The
Drafting Subagent then formulates the reply using only that evidence. This
means:

* It cannot invent experience you
  don't have.

Use **Preference Memory MCP**. It is a
local, provider-neutral MCP server that turns user corrections into
**scoped, reviewable, and safely retrievable preference
memory** stored in SQLite. Critically, every
inferred memory starts as `pending` and
**never activates without explicit user
confirmation**. You review and approve
preferences in a local CLI, and the server returns the matched scope with every
recall, so the agent knows *why* a preference applies.[-6](https://glama.ai/mcp/servers/efficjump/preference-memory-mcp/tree#main-content#1)

### 3. Learned Patterns (mined rules)

These are automatically induced from the
decision ledger. When the same category of decision appears consistently, the
system proposes a **deterministic
rule** that can bypass the LLM entirely on
future matches.

Use the
**`@model-action-protocol/core`
LearningEngine**. It analyzes the ledger for
repeated correction patterns and proposes rules after observing them a
configurable number of times (e.g., 3+). Proposed rules **require human approval before activating**. Once approved, they become a "fast tier" that runs in microseconds,
and the LLM only fires for patterns the rules haven't seen yet.[-30](https://www.npmjs.com/package/@model-action-protocol/core?activeTab=versions#2)

The learning engine also exports
**agent memory**—lessons
distilled from past actions that can be injected into the Decision Router's
prompt as learned context.[-30](https://www.npmjs.com/package/@model-action-protocol/core?activeTab=versions#2)

-------------------------------------------

The existing three-stage pipeline (CV
Analyst → Drafting → Decision Router) gains a **fourth stage** that runs
*after* your briefing decisions
are recorded and *before* the
next cycle:

Stage D — Learning:
  1. Append every decision to the decision ledger.
  2. Run pattern mining (LearningEngine.analyzePatterns) over the ledger.
  3. If a pattern meets the threshold, propose a rule and present it to you

The Learning Subagent does
**not** modify any live

🔄 How Learning Changes the Decision Router
------------------------------------------

The Decision Router from the previous
plan now checks **four sources of
truth** before escalating to you, in this
order:

### Source 1: Approved Learned Rules (fastest, deterministic)

Before calling any LLM or confidence
gate, the router checks the `learned_patterns`
table. If an approved rule matches the event, it executes the prescribed action
immediately—**no LLM call, no
briefing**. This is the "microsecond
gate".[-30](https://www.npmjs.com/package/@model-action-protocol/core?activeTab=versions#2)

Example rule:
`IF classification = 'tech_question' AND entity IN ('Kubernetes', 'Go', 'Python') AND cv_evidence_found = true THEN auto_send`.

### Source 2: Preference Memory (scoped constraints)

If no hard rule matches, the router
queries Preference Memory MCP for scoped preferences. A preference can
**modify** the routing
decision even if it doesn't fully automate it—for example, a preference might
say "always add a 15-minute buffer before calls" or "never propose Friday
afternoons." Preferences are constraints, not full rules.

### Source 3: Dynamic Few-Shot Examples (style and judgment)

The Drafting Subagent no longer uses a
static prompt. For each new event, the harness retrieves the
**most similar past decisions** from the ledger—by embedding similarity or keyword match—and injects
them as few-shot examples into the prompt. This is "dynamic few-shot selection":
pulling examples from a library based on input similarity rather than using
static examples.

If you consistently edit drafts to be
shorter, more direct, or more enthusiastic, the dynamic examples will surface
those edits, and the model will gradually match your style without any
fine-tuning.

### Source 4: Recalibrated Confidence Gate (the safety net)

Only after the first three sources fail
to resolve the action does the router call
`mcp-confidence`. But the thresholds are no longer
defaults—they are **recalibrated on your own
decision history**.

`mcp-confidence` explicitly
warns: "The defaults are provisional guesses. Do not turn on auto-accept routing
until you've recalibrated on your own model". The tool
bundles risk-coverage analysis that turns a log of real traffic into the
thresholds your model needs. Your decision ledger is that
traffic log.[-16](https://pypi.org/project/mcp-confidence/#1)

The router also learns from
**overrides**: if an action
was auto-approved but you later edited or rejected it, that is logged as a
"human override of an auto-approved action" and fed back into calibration,
lowering the confidence for that pattern.

📈 The Graduated Autonomy Ladder
-------------------------------

Autonomy is not binary. Every category
of decision climbs a ladder, and **promotion is
earned, never automatic**. This is the
lifecycle used by `learned-behavior`: every
lesson has a confidence score and a status
(`candidate → approved → dormant`), with
promotion based on consistent observations and decay based on contradiction or
inactivity.[-32](https://pypi.org/project/learned-behavior/0.1.0/#1)

| Tier | Name | Trigger to Enter | Behavior |
| --- | --- | --- | --- |
| **0** | `ask` | Default for every new category | Always brief; never auto-execute. |
| **1** | `auto_approve` | 10+ consistent approvals **or** an approved learned rule with high confidence | Execute immediately, but **show in briefing as "✅ Handled automatically."** You can still override. |
| **2** | `auto_send` | You **explicitly promote** a rule/preference to this tier. Never auto-promoted. | Execute immediately, **no briefing entry** (logged only). Reserved for low-risk, high-repetition categories. |

This matches the graduated-autonomy
pattern: "Act + Notify" at confidence ≥ 0.8 with 10+ observations, then "Silent"
only with user approval—**never
auto-promoted** to the silent tier.

**Hard safety
boundary**: `auto_send` is **disabled** for salary discussions, offer-stage threads, relocation questions, and
any action with a job-advancement score below 0.7. The Archon guide makes the
same point: "Risk-Aware: Never auto-approves destructive operations" and "Only
automates with high confidence (>90%)" with strict safety
boundaries.[-31](https://github.com/Heinvv10/Archon-Agent/blob/main/AUTO_ACCEPT_LEARNING_GUIDE.md#1)

🧠 The Briefing Gains a Fourth Section
-------------------------------------

Your briefing now has
**four sections**:

1. **✅ Handled
   automatically** — actions taken since
   your last check (read-only summary).
2. **📬 Needs your
   decision** — the main queue (approve /
   edit / reject / don't ask again).
3. **⚠️ High
   priority** — salary, offer stage,
   low-confidence drafts.
4. **🧠 Suggested
   automation** — *new.* The Learning Subagent's
   proposals:

   * "You have approved 7
     replies to Kubernetes questions without edits.
     **Create a rule to auto-send these in
     the future?**"
   * "You consistently edit
     scheduling replies to add a 15-minute buffer.
     **Save this as a
     preference?**"
   * "Rule
     `recruiter_availability_reply` has
     been contradicted twice this week. **Demote it from `auto_send` to `auto_approve`?**"

Every proposal is **opt-in**. Nothing activates without
your click.

⚠️ Safety Rails for the Learning System
---------------------------------------

1. **The ledger is
   immutable.** The learning engine reads
   from it but never modifies it. Every proposed rule traces back to the
   exact decisions that generated it.[-30](https://www.npmjs.com/package/@model-action-protocol/core?activeTab=versions#2)
2. **No self-promotion to
   `auto_send`.** The system can *propose* promotion, but only you
   can activate it. This is enforced in code, not just policy.
3. **Rules
   decay.** An approved rule that has not
   matched any event in 60 days loses confidence and eventually goes
   dormant, dropping out of routing. This prevents
   stale rules from silently automating decisions based on outdated
   behavior.[-32](https://pypi.org/project/learned-behavior/0.1.0/#1)
4. **Overrides demote
   immediately.** If you edit or reject an
   auto-executed action, the matching rule is **demoted one tier** and flagged
   for review in the next briefing. This is the single most important
   feedback signal.
5. **Shadow mode before live
   promotion.** Before a rule moves from
   `candidate` to
   `approved`, it runs in shadow mode for a
   configurable period: the router logs what it *would have* done, but still
   briefs you. Only if the shadow log matches your decisions does the rule
   become eligible for promotion.
6. **Calibration before
   trust.** Auto-accept routing stays off
   until `mcp-confidence` has been
   recalibrated on your own ledger—not the defaults.[-16](https://pypi.org/project/mcp-confidence/#1)

💎 Updated Stack Summary (New Components Only)
---------------------------------------------

| Component | Tool / Approach | Role in Learning |
| --- | --- | --- |
| **Decision Ledger** | `ledgerchain` (SQLite) | Immutable training data; tamper-evident audit |
| **Preference Memory** | `Preference Memory MCP` | Scoped, reviewable corrections with `pending` lifecycle |
| **Pattern Mining** | `@model-action-protocol/core` LearningEngine | Proposes deterministic rules from repeated decisions |
| **Confidence Recalibration** | `mcp-confidence` calibration tooling | Turns your decision log into honest per-model thresholds |
| **Dynamic Few-Shot** | Custom retrieval over `ledgerchain` (or `feedloop` for preference pairs) | Injects similar past decisions into the drafting prompt |
| **Autonomy Lifecycle** | Custom, modeled on `learned-behavior` | `candidate → approved → dormant`, with decay and override demotion |

The total recurring cost remains
**the LLM API and nothing else**. Every learning component is local, free, and audit-friendly.

The key architectural shift is this:
**the Decision Router is no longer a static
classifier—it is a layered judge.** Approved
learned rules handle the routine cases in microseconds. Preferences constrain
the LLM's freedom. Dynamic examples teach it your style. Only the genuinely
novel or high-stakes cases reach the confidence gate and then reach you. Over
time, the briefing shrinks—not because the agent is taking unchecked risks, but
because it has **earned** the right to act through a documented, reversible, human-approved
learning loop.
